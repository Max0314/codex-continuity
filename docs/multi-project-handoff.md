# 多项目交接与边界情况

## 1. “发布交接”针对什么范围

默认针对一台电脑的固定工作根目录，而不是单个项目。

例如：

```text
D:\code_CPL
  codex-continuity\
  bi_center\
  code_CPL\
  ai_code_review_web\
  ...
```

执行一次 `continuity publish`，客户端会聚合整个根目录下的 Git 项目和相关 Codex 会话。服务端保存一份“工作区交接”，管理端可以显示其中包含多少项目和多少会话。

## 2. 是否要求两台电脑目录完全相同

不强制要求绝对路径相同，但推荐两端都使用 `D:\code_CPL`。

客户端使用：

- 工作根目录名称作为工作区身份的一部分；
- 项目相对于根目录的路径；
- Git commit、branch 和 remote 名称；
- 设备本地配置中的根目录映射。

因此下面也可以工作：

```text
办公室电脑：D:\code_CPL\bi_center
公司电脑：  E:\work\code_CPL\bi_center
```

两端根目录同名、相对目录一致时最省心。

## 3. 发布时对话仍在进行

`publish` 会先扫描会话文件大小，再按该长度读取，因此形成一个明确的快照边界。

- 扫描前已写入的内容进入本次快照；
- 扫描后继续产生的消息不会保证进入本次快照；
- 对话可以继续，不会被客户端停止；
- 离开电脑前可以再次执行 `publish` 生成更新版本。

未来托盘版可以观察 Codex 是否仍活跃，在当前回合结束后自动补一份快照。

## 4. 两台电脑同时修改同一项目

当前 MVP 不会自动覆盖代码或切换分支。

- Git 仓库仍以 GitHub/GitLab 为源代码同步渠道；
- 交接包记录 commit、branch、dirty 状态和补丁；
- `takeover` 只解压到 `.codex-continuity/handoffs/<id>`；
- 用户/Codex 先核对目标工作树，再决定应用补丁或继续开发。

下一阶段将增加 lease 和 dirty 工作树冲突阻断。

## 5. 会话文件很大

当前限制：

- 单个 Codex 会话最多 128 MiB；
- 一份交接中会话总量最多 350 MiB；
- 最多考虑最近 30 条相关会话；
- 默认服务端上传上限 512 MiB。

超过限制的会话会在 `manifest.json` 标记跳过原因，不会让整次发布失败。

后续会使用内容寻址和增量分块，避免重复上传大型历史会话。

## 6. 服务端离线

当前 CLI 会返回明确错误，不会丢失本机项目数据。MVP 尚未保留断网队列。

下一阶段后台客户端将：

- 先把加密包写入本地队列；
- 网络恢复后重试；
- 成功收到服务端回执后再标记已发布。

## 7. 原任务能否原样继续

不能承诺把两台本地电脑上的 Codex 任务 ID 和内部数据库原样合并。

当前可靠模型是：

1. 保存原任务的只读会话快照；
2. 保存 Git 与项目状态；
3. 在目标电脑生成结构化继续入口；
4. 创建或使用一个新的 Codex 任务继续。

这避免直接复制内部数据库造成索引损坏、任务丢失或版本不兼容。
