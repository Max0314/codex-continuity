# Codex Continuity 产品范围校准

日期：2026-07-27

## 结论

产品应统一命名为 **Codex Continuity**，中文说明使用“Codex 对话同步”。

当前版本的服务端、加密传输、桌面壳、托盘入口和批量工作区扫描有保留价值，但产品主流程确实偏大。它现在更像“跨设备开发工作交接平台”，而用户当前真正需要的是：

1. 找到与工作区相关的 Codex 会话；
2. 加密导出、上传和下载；
3. 在另一台电脑恢复上下文；
4. 后台自动完成同步；
5. 尽可能继续原对话。

因此不建议推翻重写，应保留基础设施，重做桌面端信息架构和同步核心。

## 当前能力核验

| 需求 | 当前状态 | 事实说明 |
|---|---|---|
| 一次处理多个项目 | 已实现 | `publish` 扫描固定根目录，不需要逐个项目打开 Codex 对话 |
| 发现相关 Codex 会话 | 已实现基础版 | 扫描 `~/.codex/sessions`，按会话 CWD 是否位于工作根目录下筛选，最多取最近 30 条 |
| 加密上传、下载 | 已实现 | 客户端本地打包、加密，服务端只保存密文 |
| 另一台电脑下载交接 | 已实现 | `takeover` 下载并解密到 `.codex-continuity/handoffs/<id>` |
| 导出聊天记录 | 部分实现 | 原始 JSONL 只读快照会被放入交接包 |
| 导入聊天记录到 Codex | 未实现 | 当前只解压快照并生成 `HANDOFF.md`，不会写入 Codex 内部会话存储 |
| 继续工作上下文 | 部分实现 | 新开 Codex 对话并读取 `HANDOFF.md` 可以语义续接 |
| 继续同一个原生 Codex 对话 | 未实现，不能承诺 | 当前没有跨主机导入原 thread 的实现 |
| 自动同步 | 未实现 | UI 开关目前只保存 `auto_sync` 设置；没有后台监听、上传队列、自动拉取或冲突处理 |
| 断网续传与失败重试 | 未实现 | 尚无持久化队列、退避重试和断点游标 |
| 双向冲突处理 | 未实现 | 尚无版本游标、设备竞争和删除传播策略 |
| 无 PowerShell 日常操作 | 已实现 | Tauri 主窗口和托盘可以调用内置核心程序 |
| 私有服务器无需访问 OpenAI | 已满足架构要求 | 服务端只负责用户、设备、元数据和密文存储 |

需要特别注意：浏览器预览中的状态和示例数据是 Mock，不能据此认定后台自动同步已经运行。

## “继续对话”的两个层级

### A. 语义续接

目标电脑创建新 Codex 对话，自动附带上一台电脑的对话摘要、未完成事项、工作区、Git 状态和必要的历史片段。

这是可稳定商用的 MVP，当前项目已有交接包基础。

### B. 原线程续接

目标电脑打开原 thread ID，并在原历史后继续追加消息。

Codex app-server 提供本机的 `thread/list`、`thread/read` 和 `thread/resume`，适合用作本机会话适配层。但它没有提供把任意外部快照导入另一台主机线程存储的稳定跨主机接口。因此：

- 可以优先通过 app-server 读取和恢复本机已有会话；
- 不应直接覆盖 Codex 内部数据库或默认 `CODEX_HOME`；
- 跨主机原线程迁移只能作为实验能力，不能成为当前商业承诺；
- 如果官方以后提供跨主机导入或桌面端 handoff 接口，再升级为原线程续接。

## 建议保留和删除的产品范围

### 保留为核心

- Windows 桌面客户端和系统托盘；
- Docker Compose 私有服务端；
- 登录、用户、设备和令牌；
- 客户端加密、密文存储；
- 会话发现、导出、下载和恢复；
- 后台同步状态、失败重试和冲突提示；
- 多设备和工作目录逻辑映射；
- 服务端管理页面。

### 从日常主界面移出

- “受管工作区 / 待接管 / 今日上传”四张运营指标卡；
- 独立的工作区、交接记录、同步规则、活动日志五级导航；
- 每次启动都展示的三步快速测试；
- 以 Git 补丁和工作区交接为主的操作语言；
- 单项目“发布交接”作为首要操作。

这些能力可以留在“高级设置 / 诊断 / 服务端管理”中，不应占据日常主流程。

## 推荐的信息架构

桌面主窗口只保留三个入口：

1. **会话**：最近 Codex 会话、所属项目、同步状态、搜索、导出和“在此设备继续”。
2. **同步**：连接状态、上次同步、失败任务、冲突处理和“立即同步”。
3. **设置**：服务地址、设备名、加密密钥、目录映射和高级诊断。

主界面只需要回答三个问题：

- 服务是否连接；
- 最近一次是否同步成功；
- 哪个对话可以在此设备继续。

## 托盘菜单

现有深色托盘菜单的结构、视觉密度和交互方式应保留。它比主窗口更符合日常高频操作。

建议只调整文案和对象：

- `Codex 工作接力` → `Codex Continuity`
- `发布本机交接` → `立即同步`
- `接管最新交接` → `在此设备继续`
- `工作区` → `最近会话`
- 每行显示：会话标题、项目名、同步状态
- 保留“自动同步”“最近活动”“打开主窗口”“设置”“退出”

正常状态下，用户不需要打开主窗口。

## 推荐架构

### 客户端

- **Session Adapter**：优先通过 Codex app-server 的公开线程接口发现、读取和恢复本机会话；只读文件快照作为兼容回退。
- **Sync Engine**：增量哈希、去重、离线队列、重试、拉取、冲突检测和删除策略。
- **Resume Adapter**：稳定版生成语义续接包；实验版验证 app-server 与隔离会话存储。
- **Tray UI**：日常主入口。
- **Main UI**：首次配置、会话管理、异常处理。

### 服务端

- 用户、设备、令牌与配额；
- 加密对象存储；
- 会话版本、同步游标和设备确认；
- 管理后台；
- 不调用 OpenAI，不解析会话正文。

不需要把 Skill 或 MCP 作为核心依赖。Skill 可以后续帮助 Codex 读取续接包；MCP 可以提供管理工具，但二者都不能替代持续运行的本地同步引擎。

## 正常工作流

### 首次配置

1. 安装客户端并登录或填入设备令牌；
2. 设置服务器地址、设备名和共享加密密钥；
3. 选择 `D:\code_CPL` 作为逻辑工作根目录；
4. 执行一次连接与加密上传测试；
5. 开启自动同步。

### 日常工作

1. 用户照常在 Codex 中工作；
2. 客户端后台发现会话变化并形成增量密文；
3. 断网时进入本地队列，恢复网络后自动上传；
4. 另一台电脑自动拉取元数据和密文；
5. 用户从托盘选择最近会话并点击“在此设备继续”；
6. 如果原线程可由官方接口恢复，则直接恢复；否则新建 Codex 对话并注入续接上下文。

用户不需要在 PowerShell 操作，也不需要向每个 Codex 对话发送“发布交接”。

## 分阶段实施

### P0：收敛和证明

- 完成品牌重命名；
- 主窗口减为“会话 / 同步 / 设置”；
- 用 app-server 建立只读会话清单；
- 实现手动“立即同步”；
- 实现可靠的语义续接；
- 明确显示“原对话续接”或“新对话续接”。

### P1：真正自动同步

- 后台变化监听；
- 增量分块和内容去重；
- 持久化离线队列；
- 自动拉取和设备确认；
- 版本冲突、删除传播和保留策略；
- 可解释的同步状态。

### P2：原线程实验与企业化

- 验证 app-server 跨版本兼容；
- 在隔离存储中验证线程恢复，不覆盖默认 Codex 数据；
- 等待或接入官方跨主机线程能力；
- 增加团队配额、审计和客户端签名升级。

## 产品验收底线

只有满足以下条件，界面才能显示“自动同步已开启”：

- 后台监听正在运行；
- 变更已经入持久化队列；
- 上传失败会自动重试；
- 另一设备能自动拉取；
- 重复数据不会重复上传；
- 冲突不会静默覆盖；
- 用户能看到最后成功时间和失败原因。

## 视觉审查

1. **概览页：功能完整但认知负担偏高。** 优点是连接状态、主要操作和工作区一屏可见；风险是指标卡、工作区、快速测试和活动流同时争夺注意力，主目标“同步会话并继续”不突出。
2. **设置页：结构清楚，可保留。** 基础配置分组合理，适合首次配置；应把测试放入设置或诊断，不再出现在每日概览。
3. **托盘菜单：健康，应成为主要入口。** 层级短、深色视觉稳定、高频动作集中；只需改名、改文案，并将工作区列表切换为最近会话。

可访问性限制：

- 多处辅助文字只有 8–11px，商业版本应提高到至少 12px；
- 工作区表格中的图标操作按钮缺少可见名称，需补充可访问名称和悬浮提示；
- 浅灰辅助文字与状态色需要做 WCAG 对比度复核；
- 本轮为视觉与代码静态审查，尚未完成键盘全流程和屏幕阅读器测试。
