# ADR-0003：客户端与服务端继续使用同一仓库

状态：已采纳
日期：2026-07-28

## 决策

Codex Continuity 当前继续使用单一 Git 仓库，但保持清晰的逻辑边界：

```text
desktop/       Windows 桌面界面与 Tauri 壳
cmd/client/    Go 客户端 sidecar
cmd/server/    Go 服务端
internal/      协议、加密、存储和领域实现
web/           服务端管理网页
deploy/        容器与部署配置
scripts/       构建、打包和发布脚本
docs/          产品、架构、部署和审计文档
```

客户端安装包和服务端容器是两套独立产物，部署与运行互不绑定；“同一仓库”只表示它们在同一个版本基线中开发和发布。

## 原因

- 会话包格式、API、鉴权、大小限制和兼容策略需要客户端与服务端同步演进；
- 当前由同一产品团队维护，原子提交可以同时修改协议两端和兼容测试；
- 一个版本号、一个发布标签即可对应桌面安装包、服务端镜像和部署文档；
- 共享 Go 领域代码能减少加密、校验和模型定义的重复实现；
- 当前仓库规模尚小，拆分会增加跨仓库变更、版本对齐和 CI 管理成本，但不会带来实际交付收益。

## 边界要求

- 桌面端不得直接依赖服务端数据库或文件布局，只通过版本化 HTTP API 通信；
- 服务端不得依赖桌面运行环境或 WebView2；
- 发布产物分别命名、构建和部署；
- API 或密文格式发生不兼容变化时，必须增加版本号和兼容测试；
- 私有部署配置不得写入仓库，令牌、密码和共享密钥不得提交。

## 何时考虑拆分

出现以下任一情况后重新评估：

1. 客户端与服务端由不同团队负责，发布节奏长期独立；
2. 服务端代码需要更严格的访问控制，而客户端计划公开；
3. 仓库体积或 CI 时间已经明显影响交付；
4. 同一服务端需要稳定支持多代客户端，必须形成独立 SDK 与兼容矩阵；
5. 服务端演进为独立商业产品，拥有单独的版本、部署和运维生命周期。

若未来拆分，应先提取版本化协议定义和兼容测试，再迁移仓库；不应先物理拆分、再补边界。
